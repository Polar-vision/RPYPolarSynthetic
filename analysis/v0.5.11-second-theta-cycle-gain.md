# v0.5.11-second-theta-cycle-gain

## Request

Clarify whether the second `theta-only` stage in `Experiment 5` is actually useful.

The concern was:

```text
theta-only only optimizes roll/pitch
phi-only only optimizes yaw

When we do the second theta-only stage,
theta-only is unrelated to yaw,
so it does not use the optimized yaw at all.

Then does the second staged cycle bring no real gain?
```

## Short Answer

In the idealized mathematical sense, your reasoning is basically correct.

For this repository's current parameterization:

- `theta-only` is exactly independent of optical-axis `yaw`;
- so the second `theta-only` stage does **not** gain new geometric information from the first `phi-only` update;
- therefore, if the first staged cycle already solved its subproblems well, a second staged cycle should add little or no theoretical benefit.

So the second cycle in `Exp5` should **not** be interpreted as a new decoupling principle.

It is better interpreted as a practical numerical-stability choice for the larger airborne problem.

## Why `theta-only` Is Independent Of `yaw`

The key implementation pieces are:

- `rpy_matrix(params) = Rz(yaw) Ry(pitch) Rx(roll)`
- `theta = atan2(sqrt(x^2 + y^2), z)`

See:

- [geometry.py](/E:/zuo/projects/RPYPolarSynthetic/src/rpy_polar_synth/geometry.py:47)
- [geometry.py](/E:/zuo/projects/RPYPolarSynthetic/src/rpy_polar_synth/geometry.py:63)

If a camera-frame ray before yaw rotation is:

```text
u = [ux, uy, uz]
```

then after optical-axis yaw:

```text
q = Rz(psi) u
```

we still have:

```text
qx^2 + qy^2 = ux^2 + uy^2
qz = uz
```

Therefore:

```text
theta(q) = atan2(sqrt(qx^2 + qy^2), qz)
         = atan2(sqrt(ux^2 + uy^2), uz)
```

which is independent of `psi`.

So in this convention, `theta` does not "see" optical-axis yaw at all.

## What The Code Actually Does

In `free_xyz_ba_experiment.py`, the staged solver does:

```text
for cycle in staged_cycles:
  solve theta-only over roll/pitch with yaw fixed
  solve phi-only over yaw with roll/pitch fixed
then run one final joint BA
```

Relevant code:

- [free_xyz_ba_experiment.py](/E:/zuo/projects/RPYPolarSynthetic/src/rpy_polar_synth/free_xyz_ba_experiment.py:671)
- [free_xyz_ba_experiment.py](/E:/zuo/projects/RPYPolarSynthetic/src/rpy_polar_synth/free_xyz_ba_experiment.py:686)

And the `theta-only` residual literally keeps only `dtheta`:

- [free_xyz_ba_experiment.py](/E:/zuo/projects/RPYPolarSynthetic/src/rpy_polar_synth/free_xyz_ba_experiment.py:526)

So the second `theta-only` pass does not consume the updated `yaw` estimate in any geometric sense.

## Does The Second Cycle Have Zero Gain?

### In Theory

If:

- centers are fixed,
- points are fixed,
- the `theta-only` subproblem is solved well in the first pass,
- and the `phi-only` subproblem is also solved well,

then repeating:

```text
theta-only -> phi-only
```

should be almost redundant.

That is because:

- the second `theta-only` problem is essentially the same as the first one;
- and if `roll/pitch` stays the same, the second `phi-only` problem is also essentially the same as the first one.

So there is no strong new information flow:

```text
phi update -> improved yaw -> better theta objective
```

That pathway does not exist here.

## Why It Can Still Help A Little In Practice

The main practical benefit is numerical, not geometric.

Possible reasons:

- each sub-solve has a finite iteration budget (`max_nfev_per_stage`);
- trust-region / robust-loss optimization may stop short of the exact block optimum;
- restarting a block solve can act like giving that block another optimization budget;
- the larger airborne problem is simply harder numerically than Exp4.

So the second cycle is better understood as:

- a continuation / stabilization trick,
- not a fundamentally new source of observability.

This is also consistent with the README statement that Exp5 uses the extra cycle mainly to make the larger strip-block stable enough to test the story fairly.

## Important Asymmetry

There is still one meaningful directional dependence:

- `phi-only` depends on the current `roll/pitch`;
- but `theta-only` does not depend on the current `yaw`.

So:

- first doing `theta-only`,
- then doing `phi-only`

still makes sense.

But doing:

- `theta-only -> phi-only -> theta-only`

does **not** create a symmetric feedback loop.

That is exactly why your question is important.

## Best Interpretation For Exp5

The most accurate interpretation is:

```text
Exp5 uses one polar_staged solver
with two staged cycles mainly as a practical numerical stabilization choice,
not because the second theta-only pass introduces new yaw-conditioned geometry.
```

## Selected Q&A

### Q1

So is the second `theta-only` stage theoretically unnecessary?

### A1

Under this repository's exact `theta / optical-axis-yaw` decoupling and with well-converged sub-solves, yes, it is largely theoretically redundant.

### Q2

Then should the repository claim that "multiple staged cycles always help"?

### A2

No. That would be too strong.

For this codebase, multiple cycles should be described more cautiously as a practical stabilization heuristic for the larger airborne block.

### Q3

Would this conclusion change if `theta` were not exactly yaw-invariant?

### A3

Yes.

If the parameterization or measurement model broke the exact invariance, then later `theta` passes could genuinely benefit from updated `yaw`.

But in the current repository, the intended design is precisely to preserve that decoupling.
