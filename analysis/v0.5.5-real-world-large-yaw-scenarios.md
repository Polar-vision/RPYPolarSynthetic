# v0.5.5-real-world-large-yaw-scenarios

## Request

Clarify the README statement:

```text
the repository is targeting situations where the initial optical-axis yaw can be very wrong
```

and answer:

- is that common in real problems?
- in what kinds of scenes or pipelines can it happen?

## Short Answer

Yes, but with an important qualification.

The README sentence should **not** be read as:

- every real BA problem frequently starts with `100 deg+` yaw error.

It is better read as:

- the repository deliberately uses large initial optical-axis `yaw` error as a **stress axis** to expose a broader bad-initialization problem.

So the practical claim is not:

- "huge yaw errors are always common"

but rather:

- "real systems do encounter cases where the pose around the viewing direction is much less reliable than tilt, and direct joint BA can then fall into a wrong basin."

## Important Convention Reminder

In this repository, `yaw` is **not** the usual vehicle heading around gravity.

It means:

- the final in-plane rotation around the current camera optical axis.

So the practical question is really:

```text
When can the camera's rotation around its own viewing direction be badly initialized?
```

That happens more often than a naive reading of the word `yaw` might suggest.

## Is It Common In Practice?

Three levels of answer are useful.

### 1. Mild to Moderate Error

This is common.

Real systems often have cases where:

- tilt is fairly well constrained;
- but the in-plane rotation around the current viewing direction is noticeably worse.

Examples:

- gravity gives a good roll/pitch prior, but heading-like information is weak;
- vision tracks are noisy, sparse, or concentrated in a poor geometry;
- the initializer comes from a rough PnP / essential-matrix / coarse pose prior.

### 2. Large Error

This is not the default every-frame case, but it is realistic in failure or reinitialization regimes.

Examples:

- tracking has just recovered after loss;
- relocalization gives a coarse but wrong orientation guess;
- the local BA window is started from contaminated matches;
- the scene geometry makes rotation around the viewing axis weakly constrained.

### 3. Extreme Error

This is mostly a stress-test regime in the repository.

Values like:

- `100 deg`
- `140 deg`
- `170 deg`

should be read mainly as:

- controlled worst-case initialization tests,

not as a claim that ordinary pipelines see such huge errors all the time.

## What Real Scenarios Can Cause It?

### 1. Gravity-Known, Heading-Weak Initialization

If another sensor or prior gives:

- good gravity / tilt,

but not a strong in-plane orientation around the viewing direction, then the repository's staged story becomes realistic.

This is one of the cleanest real interpretations of the project:

- roll/pitch are already roughly right;
- optical-axis yaw is still poorly initialized.

### 2. Forward-Motion / Low-Parallax Windows

When the camera mostly moves forward along its viewing direction:

- parallax is weak;
- translation-depth-pose coupling is stronger;
- small image changes can be explained in multiple ways.

Typical examples:

- UAV forward flight
- body-worn or handheld forward-looking video
- endoscopic / tube-like forward motion
- monocular local BA with short baseline

This does not automatically produce huge yaw error, but it does make direct joint BA much easier to destabilize when the yaw-like part of pose is wrong.

### 3. Reinitialization After Tracking Loss

After tracking loss, a restarted local BA can begin from:

- rough feature matches,
- a weak relocalization pose,
- or a partially correct orientation prior.

Then one part of orientation may already be reasonable while the optical-axis in-plane component is still poor.

That is a very natural real interpretation of the repository's stress tests.

### 4. Repeated Texture Or Weakly Informative Appearance

Some scenes do not strongly constrain in-plane orientation:

- repeated facades
- grid-like structures
- weak texture near the center
- visually self-similar regions

Then the optimizer can start with a substantially wrong optical-axis spin and still explain the data "well enough" locally to fall into a wrong basin.

### 5. Near-Axis-Dominated Observations

If many useful measurements lie near the optical axis:

- the azimuthal information is weak;
- raw `phi` becomes unreliable;
- direct optimization can over-trust a poor orientation explanation.

This is one reason the repository separates:

- the residual-design problem (`polar_cov_joint`)
- from the initialization / basin problem (`polar_staged`)

## Why Use Large Initial Yaw As The Main Stress Axis?

Because it is a clean way to trigger the broader failure mode the project cares about:

```text
bad pose init
-> coupled BA variables absorb the error
-> optimizer enters a wrong basin
```

Large optical-axis yaw perturbation is useful experimentally because:

- it strongly excites the `phi`-related part of the model;
- it keeps the stress direction interpretable;
- it exposes when direct joint BA cannot recover a good basin on its own.

So the repository is not saying:

- "large yaw error is the only practical problem"

It is saying:

- "large yaw error is a clean and meaningful way to probe bad-basin behavior in coupled BA."

## Best README Interpretation

The most defensible reading of that README sentence is:

```text
the repository targets bad-initialization regimes where
the pose component associated with optical-axis yaw
can be much less reliable than the tilt component,
especially in coupled BA problems.
```

That interpretation is stronger and more realistic than the literal reading:

```text
real systems constantly have enormous yaw errors
```

because the latter is not really what the experiments are trying to claim.

## Selected Q&A

### Q1

Does the repository only help when yaw initialization is bad?

### A1

No.

The controlled experiments mainly use large optical-axis yaw error as the stress axis, but the deeper issue is:

- bad pose initialization inside a coupled BA problem.

Yaw is just the cleanest variable to perturb in this project's geometry.

### Q2

So is this mainly a failure-recovery story rather than a normal-tracking story?

### A2

That is a very good practical reading.

The strongest motivation is:

- hard local BA windows,
- recovery / relocalization cases,
- or geometrically weak windows,

where a direct joint solve is much more likely to start in the wrong basin.
