# v0.5.7-polar-staged-vs-alternating-ba

## Request

Clarify two questions:

1. How is this repository's `polar_staged` different from older alternating BA schemes that repeatedly solve points and pose in turn?
2. Is it reasonable for an expert to question whether alternating optimization is worse than full joint optimization because the latter is more consistent with the global optimum?

## Short Answer

Yes, that expert concern is reasonable.

But the correct response is:

- `polar_staged` is **not** claiming that alternating optimization is intrinsically superior to fully joint optimization in terms of asymptotic optimality;
- it is claiming that, in these synthetic hard-initialization BA regimes, a short staged front-end can move the problem into a basin where the final joint optimization becomes much more reliable.

So the repository's method is not:

- "replace joint BA with endless alternating pose / point updates"

It is:

- "use a geometrically informed staged initializer, then return to full joint BA."

## Main Difference From Classical Alternating BA

Classical alternating BA usually means something like:

```text
repeat until convergence:
  update pose with points fixed
  update points with pose fixed
```

or some close block-coordinate variant.

That style has three key characteristics:

1. it alternates over the **full optimization variables**;
2. it is typically used as the main solver, not just as an initializer;
3. its block split is mainly algebraic or computational.

`polar_staged` in this repository is different in all three ways.

### Difference 1. It Does Not Alternate Pose And Structure

The staged blocks are not:

- pose block
- structure block

Instead they are:

- `theta-only` tilt block
- `phi-only` optical-axis-yaw block

and the BA variables like:

- inverse depth
- translation
- free `XYZ`

are intentionally **frozen** during staged initialization.

That is explicit in the implementation:

- `experiment.py` staged pose-only update fixes `yaw` while solving `roll/pitch`, then fixes updated tilt while solving `yaw`
- `ba_experiment.py` explicitly keeps inverse depths fixed during staged initialization
- `free_xyz_ba_experiment.py` keeps centers and points fixed during staged cycles

So this is not a pose/point alternation. It is a **geometry-stratified pose initialization**.

## Difference 2. It Is A Short Initializer, Not The Final Solver

The repository always returns to a final full covariance-aware joint solve.

That matters a lot.

The method is:

```text
restricted staged updates
-> produce a better initial basin
-> run full joint BA
```

So the staged part is not presented as the final estimator of record. The final estimator is still the fully joint one.

This is very different from claiming:

```text
block coordinate descent itself is better than full joint BA
```

which would be a much stronger and harder claim.

## Difference 3. The Block Split Is Geometric, Not Merely Computational

The split used here is motivated by:

- `theta` mainly informing tilt
- `phi` mainly informing optical-axis yaw

So the staged decomposition is built around a specific observation geometry.

In contrast, older alternating BA methods often split variables because:

- the Schur structure is convenient;
- point updates are cheap;
- or subproblems have simpler linearization.

That is a different rationale.

This repository is not saying:

- "any block split helps"

It is saying:

- "this particular `theta/phi` split helps because it lines up with the camera observation geometry."

## Is The Expert's Criticism Reasonable?

Yes.

If the criticism is:

```text
In principle, if you can solve the full joint problem well,
that is the cleaner route to the true optimum.
Why introduce alternating or staged sub-solves?
```

that is a perfectly reasonable expert concern.

For a smooth nonconvex problem, a full joint formulation is often the most faithful expression of the model.

So the right answer is **not**:

- "alternating is theoretically superior"

The right answer is:

- "the practical issue is not only model fidelity, but basin entry."

## The Repository's Real Position

This project is about a particular failure mode:

```text
bad initialization
-> strong coupling
-> direct joint BA explains pose error using the wrong variables
-> optimizer enters a wrong basin
```

In that setting, a fully joint solver may be more elegant in formulation and still behave worse in practice because it is allowed to move all coupled variables too early.

So the staged method is an answer to:

```text
How do we get the optimizer into a basin
where the final full joint solve can actually succeed?
```

That is a different question from:

```text
What objective would be ideal if global optimization were easy?
```

## Does `polar_staged` Claim Better Global Optimality?

No.

It does not prove:

- better global optimality guarantees;
- better asymptotic consistency;
- or superiority over a hypothetical globally convergent full joint solver.

Its claim is much narrower:

- under the tested synthetic hard-initialization BA regimes,
- a short geometry-informed staged front-end enlarges the practical convergence basin.

That claim is consistent with the experiments.

## Why The Objection Still Matters

The objection matters because it keeps the claim honest.

An expert is right to ask:

- is this really a better estimator,
- or just a useful initializer?

Based on the repository as it stands, the more defensible answer is:

- `polar_staged` is primarily a better initializer / basin-rescue strategy,
- followed by the same final joint BA family.

That framing is stronger scientifically than overselling it as a universally superior optimizer.

## Best Comparison Sentence

The cleanest way to compare them is:

```text
Classical alternating BA usually alternates full pose and structure blocks as a solver.
This repository's polar_staged instead performs a short geometry-based staged pose initialization
while freezing the hardest coupled variables, then hands the problem back to full joint BA.
```

## Selected Q&A

### Q1

So is `polar_staged` just a fancy initializer?

### A1

That is actually a fair and accurate practical reading.

More specifically:

- it is a geometry-informed staged initializer for the final covariance-aware joint solver.

### Q2

Does that make the method less interesting?

### A2

Not necessarily.

In nonconvex BA problems, initializer design can be extremely important. If a structured initializer reliably moves the problem into a good basin that direct joint BA misses, that is still a meaningful contribution.

### Q3

Would the method still matter if a perfect global solver existed?

### A3

Probably much less.

The method's value is strongest precisely because practical BA is nonconvex and initialization-sensitive.
