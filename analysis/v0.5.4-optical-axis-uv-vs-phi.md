# v0.5.4-optical-axis-uv-vs-phi

## Request

Clarify the question:

```text
Near the optical axis, phi becomes physically ill-conditioned.
Does uv also become physically ill-conditioned there?
```

## Short Answer

Not in the same sense.

- `phi` becomes physically ill-conditioned near the optical axis because the ray direction is approaching the axis, so its azimuth is no longer a stable physical quantity.
- `uv` does **not** have the same coordinate singularity there. The image point remains well-defined near the principal point.

But `uv` does suffer a related information loss:

- near the optical axis, small image motions are less informative about optical-axis azimuth / yaw;
- so while `uv` is still a valid coordinate system, the specific **yaw-relevant information** is becoming weak there.

So the right distinction is:

- `phi` near the axis: **coordinate-level ill-conditioning**
- `uv` near the axis: **information becomes less discriminative for the same geometric mode**, but the coordinates themselves are still well-defined

## Why `phi` Is Ill-Conditioned

In this repository:

```text
phi = atan2(y, x)
```

when the bearing is close to the optical axis, both `x` and `y` are close to `0`.

Then:

- the azimuth angle is determined by a very small lateral component;
- tiny perturbations can cause large angular changes in `phi`;
- the "direction around the axis" is no longer physically stable.

That is why the implementation explicitly inflates the near-axis `phi` variance in:

- `src/rpy_polar_synth/geometry.py`

with the comment:

```text
Near the optical axis phi is physically ill-defined.
```

and the code:

```python
if theta < np.deg2rad(0.05):
    cov[1, 1] = max(cov[1, 1], (np.pi / 2.0) ** 2)
```

## Why `uv` Is Different

In the equidistant camera model used here:

```text
u = cx + f * theta * cos(phi)
v = cy + f * theta * sin(phi)
```

Near the optical axis:

- `theta` is small;
- therefore the image point simply approaches the principal point `(cx, cy)`.

There is no `atan2(0, 0)` singularity in the image coordinates themselves.

So:

- the pixel location remains perfectly valid;
- the camera still measures a point near the image center;
- numerical optimization in `uv` does not break just because a point lies near the optical axis.

## Then What Is Lost In `uv`?

What is lost is not the coordinate definition, but the explicit polar interpretation.

Near the axis:

- many different azimuth directions correspond to very small image displacements;
- the image point carries little clean evidence about "which way around the axis" the ray points;
- therefore the optical-axis yaw signal is weak.

So `uv` hides the same underlying geometric weakness that `phi` exposes directly.

This is why the README should not say:

- "`uv` becomes singular near the axis"

but can reasonably say:

- "`uv` does not make the azimuth ill-conditioning explicit, while polar coordinates do."

## Best Interpretation For The Project

For this repository, the cleanest way to say it is:

1. `uv` remains a valid measurement coordinate near the principal point.
2. `phi` becomes physically ill-defined near the optical axis.
3. Therefore a raw polar residual can become overconfident in a quantity that is not physically reliable there.
4. `polar_cov_joint` corrects that by propagating covariance and down-weighting `phi` near the axis.

So the near-axis issue is a stronger problem for **raw polar optimization** than for `uv_joint`, even though both are observing the same underlying geometry.

## Selected Q&A

### Q1

Does this mean `uv_joint` is automatically better near the optical axis?

### A1

Not automatically.

It means `uv_joint` does not suffer from the same explicit coordinate singularity. But `uv_joint` also does not expose the `theta/phi` decomposition that the project wants to use, and it can still struggle in the coupled BA settings for different reasons.

### Q2

So is the optical-axis issue mainly a `polar_plain_joint` problem?

### A2

Yes, that is the cleanest reading.

- `polar_plain_joint` exposes the geometry but is naive about the near-axis reliability of `phi`.
- `polar_cov_joint` is the fix that makes polar optimization statistically honest near the axis.
